# Правила разработки проекта AmoCRM Analytics

## 1. Регламент взаимодействия и планирования изменений
### Обязательный план реализации перед изменениями:
- **Сначала план**: перед началом выполнения любой задачи или внесением изменений в код/файлы ассистент обязан сначала предоставить пользователю четкий и краткий пошаговый план:
  1. Суть планируемых изменений и логика решения.
  2. Список затрагиваемых файлов (бэкенд, фронтенд, конфигурации и т.д.).
  3. Конкретные шаги реализации.
- **Ожидание подтверждения**: к непосредственному редактированию файлов или выполнению команд ассистент переходит **строго только после подтверждения плана пользователем** (за исключением случаев, когда пользователь прямо в запросе указал сделать сразу без согласования плана).

## 2. Регламент проверок, Git и Docker
Все проверки и действия должны быть максимально быстрыми, чтобы не блокировать процесс разработки.

### Запрет на автоматический запуск тестов:
- **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО автоматически запускать тесты (`pytest`, `npm test` и т.д.)** — ни при написании кода, ни перед коммитом, ни в конце задачи!
- Тестирование выполняется пользователем отдельно (в отдельном чате или терминале) после нескольких изменений.
- Ассистент запускает тесты **СТРОГО ТОЛЬКО ПО ПРЯМОЙ КОМАНДЕ ПОЛЬЗОВАТЕЛЯ** (когда пользователь прямо написал: «запусти тесты»).

### Быстрая проверка изменений:
- **Для Python**: только мгновенная проверка синтаксиса измененного файла через `python3 -m py_compile <path>` (~0.05 сек). Никаких `pytest`.
- **Для Frontend**: сборка `npm run build` выполняется только при масштабных изменениях фронтенда или по прямому запросу.

### Протокол фиксации в Git:
- Коммиты и пуши выполняются **один раз в конце цикла выполнения задачи**, когда все необходимые файлы изменены и проверены синтаксически:
  ```bash
  git add -A && git commit -m "<описание изменения>" && git push origin main
  ```
- **Защита от перезаписи**: если возникли нежелательные изменения от автосохранения IDE пользователя, восстанавливать состояние через `git restore .`.

### Быстрое обновление Docker (без долгих пересборок):
- Исходный код смонтирован в контейнеры через `volumes` (`- ./backend:/app`, `- ./crm_sync:/app`), поэтому код обновляется мгновенно.
- **Обычные изменения в коде (.py, .ts, .tsx)**:
  - Достаточно быстрого перезапуска контейнера (занимает ~1 сек):
    ```bash
    docker compose restart <service>
    ```
- **Полная пересборка (`docker compose up -d --build --no-deps <service>`)**:
  - Выполняется **ТОЛЬКО** если изменились зависимости (`requirements.txt`, `package.json`) или конфигурация `Dockerfile` / `docker-compose.yml`. В остальных случаях долгий `--build` запрещён.

## 3. Модульная архитектура (Зеркало бэкенда)
- Архитектура фронтенда и бэкенда синхронизирована по изолированным модулям:
  - **Фронтенд (`frontend/src/modules/`)**:
    - `analytics/` — единый аналитический комбайн (BI-аналитика, финансы, воронка, время на этапах, кастомные поля, причины отказа, LTV, сделки в зоне риска).
    - `quality_control/` — контроль качества звонков и речевая аналитика (аудит звонков нейросетью, транскрипции, соблюдение регламентов продаж, спасение сделок).
    - `03_ai_predictions/` — модуль предиктивной аналитики.
    - `crm_nodes/` — визуализация и управление узлами CRM (структура воронок, переходы этапов, связи и автоматизации).
    - `anomaly_deals/` — детекция и аналитика аномальных сделок (зависшие этапы, аномальные чеки, риски срыва).
    - `ai_chat/` — контекстный ИИ-ассистент по аналитике.
    - `admin/` — управление аккаунтами AmoCRM и уведомлениями.
    - `auth/` — авторизация, профиль и сессии.
    - `shared/` — переиспользуемые компоненты (FilterBar, контекст фильтров, базовый API-клиент).
  - **Бэкенд (`backend/app/modules/`)**:
    - `analytics/` — унифицированный роутер аналитики (`router.py`, `bi.py`, `stages.py`, `common.py`).
    - `quality_control/` — сервис и API речевой аналитики (`router.py`, `service.py`, фоновый воркер обработки очереди звонков, математический скоринг регламентов).
    - `crm_nodes/` — сервис и API графа узлов CRM и процессов (`router.py`, `service.py`, `schemas.py`).
    - `anomaly_deals/` — сервис и API выявления аномальных сделок и рисков (`router.py`, `service.py`, `schemas.py`).
    - `admin/` — API управления аккаунтами.
    - `ai_chat/` — API чата с LLM по аналитике.
    - `auth/` — API аутентификации.
  - **Микросервис синхронизации (`crm_sync/`)**:
    - Автономный Python-воркер фоновой синхронизации данных из AmoCRM (сделки, события, примечания, звонки).
    - **Принцип разделения ответственности**: `crm_sync` занимается **только транспортом данных** из AmoCRM в БД (валидация звонков, сохранение метаданных в статусе `pending` или `skipped`). Любая тяжёлая бизнес-логика, скачивание аудиозаписей, транскрипция и вызовы нейросетей (LLM) выполняются **исключительно внутри бэкенда**.
- Любые доработки или новые сервисы добавляются изолированно в свои папки, не затрагивая код других сервисов.
- Запрещено раздувать страницы в монолиты (выносить вкладки, фильтры и графики в отдельные компоненты по 100–300 строк).
